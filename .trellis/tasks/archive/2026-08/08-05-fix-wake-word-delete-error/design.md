# 技术设计：修复唤醒词删除服务器错误

## 根因与边界

`devices_wakeword` 在实际 PostgreSQL 数据库中缺少所有约束，尽管 Django 迁移 `0016_wakeword` 已被记录为已应用。`id=1` 因而同时存在两条记录，使 DRF 对 `/wake-words/1/` 的单对象查询无法唯一命中并返回 500。

修复必须位于数据库层：前端和 `WakeWordViewSet.perform_destroy` 的稳定 ID 契约是正确的。仅在视图层吞掉 `MultipleObjectsReturned` 不能让用户选择两条同 ID 记录中的任意一条，且会隐藏损坏数据。

## 数据修复迁移

新增 PostgreSQL 数据迁移，按以下顺序执行：

1. 从系统目录检测 `devices_wakeword` 是否已有主键；已有时立即退出，保证正常数据库无副作用。
2. 在全表范围对每个重复 ID，按 `created_at` 再按物理行标识稳定排序：最早记录保留原 ID 和现有中间表设备绑定；其余记录从当前最大 ID 之后分配新 ID。
3. 不迁移不明归属的中间表绑定到新 ID；因此不会把同一设备错误绑定到多个唤醒词。当前选定的“你好小灰”是 ID=1 的最早记录并保留绑定。
4. 将 `id` 设为非空，建立全表主键约束，并将自增序列推进至当前最大 ID，确保后续任一公司创建唤醒词都不会复用 ID。

## 兼容性与回滚

- 仅在 `devices_wakeword` 缺失主键时写入数据；已健康的生产库和测试库保持不变。
- 迁移完成后，`DELETE /api/v1/wake-words/{id}/` 继续走既有 REST API 与实时事件路径，无前端契约变化。
- 数据迁移不可通过反向迁移恢复原来的歧义绑定；反向操作为无操作。回滚应用版本前应保留已修复的数据库约束。

## 验证

- 添加迁移级回归测试：构造缺失主键、跨公司数据及重复 ID，运行迁移后断言保留最早记录的绑定、重分配后 ID 全局唯一、主键存在且序列安全。
- 添加 API 回归测试：同公司有两条不同 ID 的唤醒词时删除其中一条返回 204，另一条保持存在；跨公司唤醒词不受影响，并继续发出删除事件。
- 在 Docker Compose 后端执行目标 Django 测试和完整 devices API 测试；最后对本地实际数据核对主键、全表 ID 唯一性、序列安全，并通过 UI 删除目标词。
