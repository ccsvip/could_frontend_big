# 排查三合一接口 TTS 连读与过滤异常

## Goal

以绑定“杨老板的公司”的 `apifox` 设备为真实样本，确认智能体页面过滤规则、LLM 流式响应、`llm.tts_segment` 与最终 TTS 上游文本之间的实际关系，并规划修复，使代码只执行页面明确配置的过滤规则。

## Confirmed Evidence

- `apifox` 当前属于 tenant 24“杨老板的公司”，绑定智能体 48“智能客服助理”和清妍音色。
- 智能体 48 的草稿、已发布快照与运行时 `tts_filter_punctuation` 均为 Python `repr='\\n'`；实际字符是反斜杠 `\\` 与小写字母 `n`，不是换行符，也不包含空格。
- 真实实验只提问“你们公司有哪些产品”：`requestId=req-product-a98830c10f`、`traceId=trace-product-a98830c10f`、`conversationId=2353`。
- 原始 `answerText` 长 528 字符，包含 52 个半角空格、24 个真实换行、0 个字面 `\\n`、0 个小写 `n`、0 个反斜杠。
- 实际产生 35 个 TTS 片段；片段合计包含 0 个空格和 0 个换行。页面配置的 `\\n` 对该回答没有任何字符过滤效果，因为原文不含反斜杠或小写 `n`。
- 完整回答使用 Markdown 列表。代码隐式删除了多数 `- `、全部空格和换行；实时路径受 delta 边界影响，实际第 6 段仍出现 `-三角形LED显示屏`，同类列表项处理不一致。
- 仅按页面当前规则删除反斜杠和小写 `n` 后的文本，与 35 个片段拼接结果不相等，证明代码仍在执行页面之外的隐藏过滤。
- 阿里 CosyVoice 支持同一任务按顺序发送多个 `continue-task`；完整语句立即合成，不完整语句缓存到后续文本或 `finish-task`。本次字符变化在送到阿里之前已经发生。
- 第二次浏览器真实实验通过 `device-chat/runtime-api-console.html` 的“智能体回答”入口执行同一问题：`requestId=req-msh21kxd-1680d3`、`traceId=trace-msh21kxd-1680d3`、`conversationId=2354`。浏览器确认 `llm.delta` 拼接与 `llm.done.answerText` 完全一致，收到 31 个 `llm.tts_segment`、458 个二进制 PCM 帧、3,413,520 bytes，并到达 `tts.done` / “播报完成，可手动回放”。
- conversation 2354 原始回答为 358 字符，包含 16 个半角空格、7 个换行、4 个 Markdown 列表横线；31 个实际 TTS 片段拼接为 331 字符，三类字符均变成 0。页面字面规则 `\\n` 在原文中匹配 0 个字符；被删除差异恰好是上述 27 个空白/Markdown 字符。
- conversation 2354 的首组产品由 LLM 自带顿号：`球形LED显示屏、` 与 `内球幕LED显示屏、`，因此这一组已有文本停顿依据。但列表边界 `LED室内显示屏  \n- LED显示屏租赁、`、`LED门楣屏  \n- 室内LED照明、`、`景观照明  \n- COB小间距显示屏、` 被当前清理压成零字符边界，真正送入同一 CosyVoice task 后分别成为连续文本 `LED室内显示屏LED显示屏租赁、`、`LED门楣屏室内LED照明、`、`景观照明COB小间距显示屏、`。
- 同一页面连续三次真实基线的关键区间分别为：`llm.tts_segment → tts.ready` 34/2/1ms（中位数 2ms），`tts.ready → 首个 PCM` 884/880/754ms（中位数 880ms）；`LLM开始 → 首播报片段` 1.88/1.61/1.46s（中位数 1.61s）。三次回答长度不同，整轮完成时间不用于判断本地代码回归。
- 阿里官方 `continue-task` 限制为单条最多 20,000 字符、单 task 累计最多 200,000 字符、发送间隔不超过 23 秒；现有 80 字硬切不是供应商要求。阿里会立即合成完整语句，并缓存不完整语句直到后续文本或 `finish-task`。

## Requirements

- 最终送给 TTS 的文本只允许执行智能体页面三项规则，并固定为“不播报文本 → 表情过滤 → 字符过滤”；完整文本与流式文本必须同义。
- 语音切分只能发生在原文已有的明确停顿边界（句读、CR/LF）或回答结束处；空格、闭合括号、引号和字符长度不得单独触发切分，传输消息边界也不得被当作新增语音边界。
- 即使页面配置删除了作为边界的句读或换行，该原始位置仍可触发切片，但输出文本不得补回被删除字符。
- 禁止代码无条件清理 Markdown、列表编号、项目符号、空格、换行或其他标点；空白-only delta 不得因 `strip()` / `trim()` 判空而丢失。
- 页面必须能无歧义地表达用户是否要过滤空格、换行、反斜杠和字面字符 `n`；保存、发布、运行时必须保持同一语义。
- 网页调试播报、设备三合一、控制命令回复及各 TTS adapter 必须遵循同一契约；同一段文本只能应用一轮页面规则。
- 删除后端和前端所有 80 字任意硬切，以及仅因空格、闭合括号或引号达到 12/30 字就截断完整句子的逻辑；不以另一个更大的数字替代。
- 流式规则必须只增量处理新 delta；无排除文本时不得增加过滤前缀暂存。上游预热 task 仍有效的正常路径不得在首段前增加 ORM、网络请求或其他 awaited 操作，首个明确停顿边界到达时必须在同一次同步处理内入队。
- 改动不得改变 ASR、LLM 请求与会话、设备鉴权、控制命令执行、打断/取消、错误隔离、音频格式、WebSocket 事件类型和 `agent.done` 行为。

## Acceptance Criteria

- 对任意真实回答，按顺序拼接 TTS 片段后，结果等于仅应用页面三项规则后的文本。
- 页面未配置空格或换行时，代码不得自行删除它们。
- 页面明确配置空格或换行时，保存、发布和运行时能够识别并严格删除对应字符。
- 字面 `\\n` 不得在未明确约定时被误解为换行，也不得意外删除所有英文小写 `n`。
- 真实问题“你们公司有哪些产品”通过 `apifox` 重测时，`answerText`、规则计算结果、`llm.tts_segment` 和上游 TTS 文本逐字符可对账。
- 固定 delta 回放必须证明：超过 80 字但没有句读/换行的完整句在 `flush=False` 时保持为 remainder，不产生 TTS segment；首个明确停顿边界到达时立即 emit；`flush=True` 时剩余完整文本原样输出。
- 既有测试必须继续证明：预热发生在等待首段之前；整个回答只创建一个 CosyVoice task；后续 `continue-task` 不等待首段音频；取消、空回答和 TTS 失败不破坏资源回收或 `agent.done`。
- 修复后在同环境通过 `apifox` 连续执行三次指定问题：`llm.tts_segment → tts.ready` 中位数不得超过 102ms，`tts.ready → 首个 PCM` 中位数不得超过 1.15s。后者包含阿里公网抖动，超限必须重跑并结合“无新增首段 awaited/I/O”检查定位，不得以修改模型、音色或减少回答内容规避。
- 阿里 20,000 字符单消息上限仅作为协议异常保护：优先使用上限前最后一个真实停顿边界；若单个不可分句段自身超过上限，则 TTS 返回明确错误但 LLM 回答仍完整结束，禁止静默硬切或插入标点。
- 若预热后的 CosyVoice task 在首个安全切片出现前接近 23 秒空闲上限，关闭未使用的陈旧预热句柄并在切片到达时重新建立；禁止发送伪文本或半句话充当保活。

## Out of Scope

- 不修改该问题的知识库内容或要求 LLM 改写产品答案。
- 不更换阿里 TTS 模型、音色或协议。
- 不使用其他问题代替指定的真实回归问题。

## Decision

- 采用可视化特殊字符选项。标点输入框只显示可见字面字符；页面另设“过滤半角空格”和“过滤换行（CR/LF）”选项。
- API 与数据库继续复用唯一字段 `ttsFilterPunctuation` / `tts_filter_punctuation`，保存真实的 U+0020、CR、LF 字符，不新增第二套布尔配置。
- 现有智能体 48 的字面 `\\n` 是本次确认的历史误配置；迁移为真实空格与换行字符，不再删除反斜杠或英文小写 `n`。
- 区分“传输消息”和“语音边界”：`continue-task` 的消息边界本身不代表强制断句；应用只在原文句读/换行或回答结束后提交可播切片，CosyVoice 仍可自行缓存最终未完成语句。
- 普通文本不设业务字符硬上限；供应商协议极限由 adapter 校验并显式失败，不通过破坏句子换取成功。
