# 08. 部署流程说明

> 本文档描述 could_frontend 项目从代码到生产环境的完整部署流程，包括 Docker Compose 部署（主推）、Caddy 反向代理配置、TLS 证书管理、环境变量分层、数据库迁移、Celery 异步任务联动，以及版本更新与回滚操作。

---

## 8.1 部署架构总览

### 8.1.1 生产拓扑

```
                    Internet
                       │
                       ▼
               ┌───────────────┐
               │   Caddy :443  │  ← TLS 终止、反向代理
               └───────┬───────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   ┌─────────┐   ┌───────────┐   ┌────────────┐
   │  web    │   │  backend  │   │ (静态资源) │
   │ :5173   │   │  :8000    │   │ /static    │
   │ (Vite)  │   │ (uvicorn) │   │ /media     │
   └─────────┘   └─────┬─────┘   └────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   ┌─────────┐   ┌───────────┐   ┌────────────┐
   │  db     │   │  redis    │   │ celery     │
   │ pgvector│   │  :6379    │   │ worker/beat│
   │ :5432   │   │           │   │            │
   └─────────┘   └───────────┘   └────────────┘
```

### 8.1.2 服务职责

| 服务 | 生产职责 |
|------|----------|
| `caddy` | 唯一对外入口，TLS 终止，将 `/` 反代到 `web:5173`，后续可扩展 `/api` 直连 backend |
| `web` | 前端 Vite dev server（当前部署形态）或 `vite build` 后的静态产物 |
| `backend` | Django + uvicorn ASGI，承载 HTTP API 与 WebSocket |
| `celery_worker` | 异步任务消费者（设备心跳检测、知识库向量化、LLM 流式回调等） |
| `celery_beat` | 周期任务调度器，使用 `django_celery_beat` 的 DatabaseScheduler |
| `db` | PostgreSQL 16 + pgvector 扩展，存储所有业务数据与知识库向量 |
| `redis` | 缓存（`REDIS_CACHE_URL`）+ Celery broker（`CELERY_BROKER_URL`，默认 db 1）+ Channels layer |

### 8.1.3 部署形态说明

当前 `docker-compose.yaml` 的 `web` 服务运行的是 `npm run dev`，适合内部 / 测试环境。正式生产部署建议：

- **前端**：构建为静态产物，由 Caddy 直接托管 `dist/`，或保留 `web` 容器但改用 `npm run build && npm run preview`
- **后端**：保持 `uvicorn` 多 worker（如 `--workers 4`），前置 Caddy / Nginx 做负载与静态分发
- **数据库**：独立托管或使用云数据库 RDS，开启定期备份

## 8.2 部署前置准备

### 8.2.1 服务器要求

| 项目 | 要求 |
|------|------|
| 操作系统 | Ubuntu 22.04 LTS / CentOS 8+ / Debian 12+ |
| Docker | 24.0+ |
| Docker Compose | v2.20+ |
| 内存 | 8 GB 起步（含向量检索建议 16 GB+） |
| 磁盘 | 50 GB+ SSD（数据库与 MinIO 对象存储占用） |
| 开放端口 | 80、443（Caddy 入口）；其余端口仅内网 |

### 8.2.2 必备凭据与资源

- 域名（如 `conai.chat`）已解析到服务器公网 IP
- TLS 证书（`.pem` + `.key`），放置于 `26179784_conai.chat_other/` 或通过 `TLS_CERT_DIR` 变量指向的目录
- 阿里云百炼 / DashScope API Key（TTS / ASR / Embedding / Rerank）
- （可选）MinIO 对象存储访问凭据
- （可选）飞书机器人 Webhook（控制指令变更通知）

### 8.2.3 配置文件清单

部署前需准备以下文件（不含于版本库，需手动放置）：

| 文件 | 内容 | 示例 |
|------|------|------|
| `backend/.env` | 后端所有环境变量 | 见 7.2.4 |
| `web/.env` | 前端代理目标 | `VITE_API_PROXY_TARGET=http://backend:8000` |
| `${TLS_CERT_DIR}/conai.chat.pem` | TLS 证书 | PEM 格式 |
| `${TLS_CERT_DIR}/conai.chat.key` | TLS 私钥 | 未加密 KEY |

## 8.3 首次部署流程

### 8.3.1 步骤一：拉取代码

```bash
git clone <repo-url> /opt/could_frontend
cd /opt/could_frontend
git config core.hooksPath .githooks
```

### 8.3.2 步骤二：配置环境变量

```bash
# 1. 根目录 .env（端口与镜像源）
cat > .env <<'EOF'
WEB_PORT=5175
API_PORT=8880
DB_PORT=5433
REDIS_PORT=6580
HTTP_PORT=80
HTTPS_PORT=443
TLS_CERT_DIR=./26179784_conai.chat_other
EOF

# 2. 后端 .env（生产关键变量）
cat > backend/.env <<'EOF'
DJANGO_DEBUG=0
DJANGO_SECRET_KEY=<生成随机强密钥>
DJANGO_ALLOWED_HOSTS=conai.chat,localhost,127.0.0.1
DATABASE_URL=postgres://postgres:<强密码>@db:5432/conai
REDIS_URL=redis://redis:6379/0
CELERY_BROKER_URL=redis://redis:6379/1
MULTIMODAL_API_KEY=<阿里云 DashScope Key>
JWT_ACCESS_MINUTES=30
JWT_REFRESH_DAYS=7
BAILIAN_CREDENTIAL_ENCRYPTION_KEY=<32字节加密密钥>
CORS_ALLOW_ALL_ORIGINS=False
EOF

# 3. 前端 .env
cat > web/.env <<'EOF'
VITE_API_PROXY_TARGET=http://backend:8000
EOF
```

> **安全约束**：严禁在代码或提交中包含明文账号、密码、长期 token、API key 或临时测试凭据。所有敏感值只能放在 `.env` 文件，且 `.env` 必须被 `.gitignore` 忽略。

### 8.3.3 步骤三：构建与启动

```bash
# 构建镜像并后台启动（首次会执行迁移、种子数据、创建超管）
docker compose up -d --build

# 观察启动过程
docker compose logs -f backend

# 等待 backend 健康检查通过后，查看全服务状态
docker compose ps
```

`backend` 容器启动命令会自动完成：

1. `python manage.py migrate` — 数据库迁移
2. `python manage.py seed_operations_periodic_tasks` — 周期任务种子
3. `python manage.py collectstatic --noinput` — 静态文件收集
4. 创建默认超管（`admin` / `admin123456`，仅当不存在）— **生产环境必须立即改密**
5. `python manage.py seed_devices` — 设备种子数据
6. `uvicorn config.asgi:application --host 0.0.0.0 --port 8000 --lifespan off`

### 8.3.4 步骤四：修改默认管理员密码

```bash
docker compose exec backend python manage.py changepassword admin
```

或登录 Django Admin 后修改。

### 8.3.5 步骤五：验证部署

| 验证项 | 命令 / 地址 | 预期 |
|--------|------------|------|
| 服务状态 | `docker compose ps` | 全部 `Up (healthy)` |
| HTTPS 入口 | `https://conai.chat` | 出现登录页 |
| API 健康 | `https://conai.chat/api/v1/...` | 返回 JSON（非 502） |
| Admin 后台 | `https://conai.chat/admin/` | 登录页正常 |
| WebSocket | `wss://conai.chat/ws/...` | 可建立连接 |
| Celery worker | `docker compose logs celery_worker` | 看到 `celery@... ready` |
| Celery beat | `docker compose logs celery_beat` | 看到 `Scheduler: Sending due task` |

## 8.4 Caddy 反向代理配置

### 8.4.1 当前 Caddyfile

```
conai.chat {
    tls /etc/caddy/certs/conai.chat.pem /etc/caddy/certs/conai.chat.key
    reverse_proxy web:5173
}
```

### 8.4.2 生产强化建议

生产环境建议显式分流 `/api`、`/ws`、`/static`、`/media` 直连 backend，减轻 web 容器负担：

```caddyfile
conai.chat {
    tls /etc/caddy/certs/conai.chat.pem /etc/caddy/certs/conai.chat.key
    encode gzip zstd

    # WebSocket
    @ws path /ws/*
    reverse_proxy @ws backend:8000

    # API
    @api path /api/*
    reverse_proxy @api backend:8000

    # 后端静态与媒体
    @static path /static/* /media/*
    reverse_proxy @static backend:8000

    # 其余走前端
    reverse_proxy web:5173
}
```

### 8.3.3 TLS 证书管理

- 当前使用自有证书，放置于 `${TLS_CERT_DIR}`（默认 `./26179784_conai.chat_other`），挂载到容器 `/etc/caddy/certs`。
- 若使用 Let's Encrypt，可将 Caddyfile 改为 `tls conai.chat` 让 Caddy 自动申请，并开放 80/443 端口。
- 证书到期前需手动替换 PEM/KEY 文件，Caddy 会自动热加载。

## 8.5 数据库与迁移管理

### 8.5.1 迁移执行

迁移由 `backend` 容器启动时自动执行。手动执行：

```bash
docker compose exec backend python manage.py migrate
```

### 8.5.2 生成迁移

本地开发新增 / 修改模型后：

```bash
docker compose exec backend python manage.py makemigrations
git add backend/apps/*/migrations/*.py
git commit -m "新增 xxx 迁移"
```

### 8.5.3 数据库备份与恢复

```bash
# 备份
docker compose exec db pg_dump -U postgres conai | gzip > backup_$(date +%Y%m%d).sql.gz

# 恢复
gunzip -c backup_20260805.sql.gz | docker compose exec -T db psql -U postgres conai

# 仅备份结构
docker compose exec db pg_dump -U postgres --schema-only conai > schema.sql
```

### 8.5.4 pgvector 扩展

知识库 chunk 表使用 `embedding_vector` 向量列，依赖 pgvector 扩展。镜像 `pgvector/pgvector:pg16` 已内置，迁移会自动执行 `CREATE EXTENSION IF NOT EXISTS vector`。**不要**换成官方 `postgres` 镜像，否则向量检索功能失效。

### 8.5.5 测试库管理

后端测试优先通过容器执行，遇到已存在测试库时优先使用 `--keepdb`：

```bash
docker compose exec backend python manage.py test apps.devices.tests.test_device_authorization_api --keepdb
```

不要随意删除测试数据库。

## 8.6 Celery 异步任务部署

### 8.6.1 worker 与 beat 协作

| 服务 | 作用 | 启动命令 |
|------|------|----------|
| `celery_worker` | 消费异步任务 | `celery -A config worker -l info` |
| `celery_beat` | 周期任务调度 | `celery -A config beat -l info --scheduler django_celery_beat.schedulers:DatabaseScheduler` |

两者均依赖 `backend` 健康、`db` / `redis` 就绪后启动（见 `depends_on`）。beat 使用 `DatabaseScheduler`，周期任务配置存储在数据库中，通过 Django Admin 的「周期任务」管理。

### 8.6.2 任务清单（部分）

典型异步任务包括：

- 设备心跳超时检测（标记离线）
- 知识库文档向量化（Embedding 入库）
- LLM 流式回调处理
- 设备授权码批量生成
- 周期任务种子（`seed_operations_periodic_tasks`）

### 8.6.3 监控

```bash
# 查看已注册任务
docker compose exec celery_worker celery -A config inspect registered

# 查看活跃任务
docker compose exec celery_worker celery -A config inspect active

# Flower 监控（如启用）
# 访问 http://localhost:5555
```

## 8.7 版本更新流程

### 8.7.1 拉取新版本并重启

```bash
cd /opt/could_frontend
git pull

# 重建变更的镜像并重启
docker compose up -d --build

# 如有新迁移，backend 会自动执行
docker compose logs -f backend
```

### 8.7.2 仅更新前端

```bash
git pull
docker compose restart web
# 或重建
docker compose up -d --build web
```

### 8.7.3 仅更新后端

```bash
git pull
docker compose up -d --build backend celery_worker celery_beat
docker compose exec backend python manage.py migrate
```

> 注意：`celery_worker` 与 `celery_beat` 共用 backend 镜像，后端代码变更必须一起重建，否则任务逻辑会与 Web 进程不一致。

## 8.8 回滚流程

### 8.8.1 代码回滚

```bash
# 查看最近提交
git log --oneline -10

# 回到指定版本
git reset --hard <commit-sha>

# 重建并重启
docker compose up -d --build
```

### 8.8.2 数据库回滚

```bash
# 回滚到某个迁移
docker compose exec backend python manage.py migrate <app_label> <migration_name>

# 从备份恢复
gunzip -c backup_20260804.sql.gz | docker compose exec -T db psql -U postgres conai
```

> **警告**：数据库回滚是不可逆操作，必须先确认备份可用，并停掉写入流量的服务（celery_worker、backend）。

### 8.8.3 镜像回滚

如使用镜像仓库而非本地构建，可指定旧 tag：

```bash
docker compose down
# 修改 .env 中镜像 tag 为旧版本
docker compose up -d
```

## 8.9 健康检查与运维

### 8.9.1 健康检查配置

`docker-compose.yaml` 为关键服务配置了 healthcheck：

| 服务 | 检查方式 | 间隔 | 超时 | 重试 | 启动宽限 |
|------|----------|------|------|------|----------|
| `db` | `pg_isready` | 5s | 3s | 30 | 10s |
| `redis` | `redis-cli ping` | 5s | 3s | 30 | 5s |
| `backend` | TCP 连接 8000 端口 | 5s | 3s | 30 | 20s |

### 8.9.2 日常巡检命令

```bash
# 服务状态
docker compose ps

# 资源占用
docker stats solin_backend solin_db solin_redis

# 磁盘
docker system df

# 清理无用的镜像与卷（谨慎）
docker system prune -a --volumes
```

### 8.9.3 重启策略

所有服务统一使用 `restart: always`，Docker 或宿主机重启后会自动恢复。

### 8.9.4 日志管理

```bash
# 实时日志
docker compose logs -f backend

# 最近 200 行
docker compose logs --tail 200 backend

# 持久化日志（建议配置 docker logging driver 或外接 ELK）
```

后端日志按 logger 分级（`apps.devices`、`config.realtime`、`apps.ai_models.services.third_party_chatbots` 等），详见 `backend/config/settings/base.py` 的 `LOGGING` 配置。

## 8.10 多服务协作注意事项

本项目涉及异步任务、后台任务、WebSocket、Docker Compose 多服务协作，部署时必须同步考虑：

| 变更类型 | 影响面 | 部署动作 |
|---------|--------|----------|
| Django 模型变更 | db 数据结构、backend、celery_worker、celery_beat | 全部重建 + 迁移 |
| Serializer / API 字段变更 | backend、前端 API module、Swagger 文档 | backend + web 重建，同步更新前端类型 |
| WebSocket `type` 协议变更 | backend realtime、前端 ws client、安卓客户端 | 全端协同发布，避免协议不兼容 |
| Celery 任务签名变更 | celery_worker、celery_beat、调用方 | 同步重建 worker/beat，清空旧任务队列 |
| 设备运行时配置变更 | backend runtime config、统一 WS 推送、安卓设备拉取 | 评估安卓端兼容性，必要时灰度 |
| 第三方机器人集成变更 | `ThirdPartyChatbotIntegration.config`、对话流程 | 至少补一个两轮回归测试 |
| 前端设计 token 变更 | `tailwind.config.ts`、`styles/index.css`、所有页面 | pre-commit 守卫会拦截违规，确认无 `!`/teal 净增量 |

> **铁律**：不同公司数据必须保证 100% 隔离。任何部署变更都不得破坏 tenant scope 机制。

## 8.11 部署 Checklist

首次部署 / 重大更新前，逐项确认：

- [ ] `.env`（根目录）端口与镜像源已配置
- [ ] `backend/.env` 中 `DATABASE_URL`、`DJANGO_SECRET_KEY`、`MULTIMODAL_API_KEY` 已设置
- [ ] `DJANGO_DEBUG=0`（生产必须关闭）
- [ ] `DJANGO_ALLOWED_HOSTS` 已限定为正式域名
- [ ] `CORS_ALLOW_ALL_ORIGINS=False`（生产建议白名单）
- [ ] TLS 证书已放置且未过期
- [ ] `git config core.hooksPath .githooks` 已执行（防止违规前端代码入库）
- [ ] 默认 `admin` 密码已修改
- [ ] 数据库已备份
- [ ] `docker compose ps` 全部 healthy
- [ ] HTTPS 入口可访问
- [ ] WebSocket 可建立连接
- [ ] Celery worker / beat 已就绪
- [ ] 一台真实设备可拉取运行时配置并发起对话
