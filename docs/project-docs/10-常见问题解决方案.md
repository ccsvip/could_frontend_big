# 10. 常见问题解决方案

> 本文档汇总 could_frontend 项目在开发、部署、运行过程中常见问题的排查思路与解决方案，按问题域分类。每个问题给出 **现象 / 原因 / 解决方案** 三段式说明，便于快速定位。

---

## 10.1 环境与 Docker Compose

### Q10.1.1 `docker compose up` 拉取镜像卡住或超时

**现象**：构建或拉取镜像长时间无响应，最终报 `timeout` 或 `i/o timeout`。

**原因**：默认基础镜像走 `docker.m.daocloud.io` 镜像源，部分网络环境无法访问；或 `PYTHON_BASE_IMAGE` / `NODE_BASE_IMAGE` 指向 Docker Hub 在受限网络下拉取超时。

**解决方案**：
1. 在根目录 `.env` 中覆盖镜像源变量，切换为可访问的镜像源：

```env
PYTHON_BASE_IMAGE=registry.cn-hangzhou.aliyuncs.com/library/python:3.13
NODE_BASE_IMAGE=registry.cn-hangzhou.aliyuncs.com/library/node:20-alpine
POSTGRES_IMAGE=pgvector/pgvector:pg16
```

2. 如使用企业内网镜像仓库，配置 Docker daemon 的 `registry-mirrors`。
3. 容器内 apt / pip 源也可通过 `APT_MIRROR` / `PIP_INDEX_URL` 覆盖。

---

### Q10.1.2 backend 容器启动报 `ImproperlyConfigured: DATABASE_URL must be set`

**现象**：backend 容器一启动就退出，日志含上述错误。

**原因**：`backend/.env` 缺失或未配置 `DATABASE_URL`。`config/settings/base.py` 强制要求该变量。

**解决方案**：
1. 确认 `backend/.env` 文件存在（不是 `.env.example`）。
2. 配置：

```env
DATABASE_URL=postgres://postgres:<密码>@db:5432/conai
```

3. 容器内连接 db 服务用主机名 `db`（compose 网络内），不要写 `localhost`。
4. 重启：`docker compose up -d backend`。

---

### Q10.1.3 端口冲突导致容器无法启动

**现象**：`docker compose up` 报 `bind: address already in use`。

**原因**：宿主机 5175 / 8880 / 5433 / 6580 / 80 / 443 中某个端口已被占用。

**解决方案**：
修改根目录 `.env`，把冲突端口改为空闲端口：

```env
WEB_PORT=5176
API_PORT=8881
DB_PORT=5434
REDIS_PORT=6581
HTTP_PORT=8080
HTTPS_PORT=8443
```

修改后重启所有服务：`docker compose up -d`。

---

### Q10.1.4 容器健康检查一直不通过

**现象**：`docker compose ps` 显示 backend 长时间 `health: starting`，最终 `unhealthy`。

**原因**：
- 数据库未就绪，backend 启动时 `migrate` 失败。
- 迁移文件冲突。
- 静态文件收集失败。

**解决方案**：
1. 查看完整日志：`docker compose logs --tail 200 backend`。
2. 确认 db 健康：`docker compose ps db`。
3. 手动执行迁移定位错误：

```bash
docker compose exec backend python manage.py migrate
```

4. 如迁移冲突，回滚到上一个稳定迁移或手动解决冲突文件。

---

## 10.2 后端运行时

### Q10.2.1 API 返回 500「服务器内部错误，请稍后重试」

**现象**：请求返回 500，响应体只有通用错误信息。

**原因**：触发了未捕获异常，被 `config/exceptions.py` 的兜底分支处理。

**解决方案**：
1. 查看后端日志定位异常堆栈：

```bash
docker compose logs --tail 200 backend | Select-String -Pattern "Error|Exception|Traceback"
```

2. 关注请求头 `x-request-id` / `x-trace-id`，在日志中按 ID 检索完整链路。
3. 业务异常应通过自定义异常携带 `response_data`，让统一处理器返回可定位信息。
4. 持续 500 且日志无明确信息时，检查 Sentry（`base.py` 已初始化 sentry_sdk）。

---

### Q10.2.2 设备码接口返回 `44001` / `44004` / `44009`

**现象**：安卓设备拉取运行时配置或发起对话，返回 `44001`、`44004`、`44009` 等错误码。

**原因与解决方案**（错误码定义见 `backend/apps/error_codes/catalogue.py`）：

| 错误码 | 含义 | 解决方案 |
|--------|------|----------|
| `1001` / `44001` | 设备码不能为空 | 请求头补 `X-Device-Code` |
| `1002` / `44004` | 设备未登记 | 在后台 `/api/v1/devices/` 登记设备 |
| `1003` / `44009` | 设备码重复绑定 | 由平台管理员清理重复设备码 |
| `1004` / `44011` | 设备未绑定公司 | 在后台为设备绑定有效公司 |
| `1005` / `44012` | 公司已停用 | 恢复公司状态或换绑可用公司 |
| `1006` / `44013` | 设备已停用 | 在后台启用设备 |
| `1007` / `44014` | 设备授权已过期 | 续期设备授权 |
| `1008` / `44021` | 设备未绑定可用智能体 | 为设备绑定并启用智能体 |
| `1009` / `44022` | 设备绑定应用未启用 | 在后台启用设备绑定应用 |

---

### Q10.2.3 设备运行时配置返回的音色与后台不一致

**现象**：设备拉到的音色不是后台刚绑定的，或仍返回公司默认音色。

**原因**：违反了音色与设备绑定的语义。规则是：
- 运行时配置里的音色字段只表示 **当前设备正在使用的音色**，不返回无关设备或候选音色列表。
- `/ai-models/tts` 保存的是 **公司默认音色**，只在设备没有绑定任何音色时作为兜底。
- 设备一旦绑定音色，默认音色失效。

**解决方案**：
1. 确认设备已通过 `tts_voice` 字段绑定具体音色。
2. 检查 `DeviceApplication.tts_voices` / `DeviceApplication.voice_tones` 是否正确关联。
3. 运行时配置通知必须始终发送 **完整配置**，即使只是音色变更也要推送完整配置而非增量字段。
4. 参考 [03-核心功能模块解析.md](03-核心功能模块解析.md) 的设备运行时章节确认数据流。

---

### Q10.2.4 普通公司账号看到了其他公司数据

**现象**：A 公司登录后能看到 B 公司的设备 / 智能体 / 资源。

**原因**：违反了租户隔离铁律。可能原因：
- 视图未使用 `TenantManager`，直接 `Model.objects.all()`。
- 平台超管入口被误用，`?tenant=<id>` 没有正确隔离。
- Serializer 未过滤租户字段。

**解决方案**：
1. 多租户模型必须用 `objects = TenantManager()`，不要直接用默认 Manager。
2. 业务函数中不要散落临时绕过租户隔离的代码。
3. 平台管理员按公司浏览时，只能通过已有 tenant scope 机制访问业务列表（前端 `useTenantScopeStore` + axios 拦截器自动追加 `?tenant=<id>`）。
4. 写一个跨租户越权回归测试：A 公司 token 请求 B 公司资源 ID，断言返回 404。
5. **不同公司数据必须保证 100% 隔离**，这是不可妥协的约束。

## 10.3 数据库与 pgvector

### Q10.3.1 知识库向量化报错 `extension "vector" does not exist`

**现象**：知识库文档向量化或检索时报 pgvector 扩展不存在。

**原因**：db 容器使用了官方 `postgres` 镜像，而非 `pgvector/pgvector:pg16`。

**解决方案**：
1. 确认 `docker-compose.yaml` 的 `db` 服务镜像：

```yaml
image: ${POSTGRES_IMAGE:-pgvector/pgvector:pg16}
```

2. 如已用错镜像，需重建 db 容器（**会丢数据**，先备份）：

```bash
docker compose down db
docker volume rm could_frontend_postgres_data
# 改正镜像后
docker compose up -d db
docker compose exec backend python manage.py migrate
```

3. 迁移会自动执行 `CREATE EXTENSION IF NOT EXISTS vector`。

---

### Q10.3.2 测试运行很慢，每次都重建测试库

**现象**：`python manage.py test` 每次都花很长时间建表。

**原因**：未使用 `--keepdb`。

**解决方案**：
优先加 `--keepdb`：

```bash
docker compose exec backend python manage.py test apps.devices.tests.test_device_authorization_api --keepdb
```

遇到已存在测试库时，**不要随意删除数据库**，优先 `--keepdb`。仅在迁移变更导致 schema 不一致时才删除重建。

---

### Q10.3.3 迁移文件冲突

**现象**：`python manage.py migrate` 报 `InconsistentMigrationHistory`。

**原因**：多人并行修改同一 app 的模型，生成了冲突的迁移文件。

**解决方案**：
1. 查看迁移状态：`python manage.py showmigrations <app>`。
2. 与协作者对齐，合并迁移文件，保留线性历史。
3. 必要时回滚到冲突前：`python manage.py migrate <app> <上一个迁移名>`。
4. 删除冲突迁移，重新 `makemigrations`。
5. **不要**手改已应用过的迁移文件。

## 10.4 前端

### Q10.4.1 前端页面打开空白

**现象**：访问 `http://localhost:5175/` 白屏，控制台报接口 404 或 CORS 错误。

**原因**：`web/.env` 的 `VITE_API_PROXY_TARGET` 未配置或指向不可达的后端。

**解决方案**：
1. 配置 `web/.env`：

```env
VITE_API_PROXY_TARGET=http://backend:8000
```

2. 确认 backend 容器健康：`docker compose ps backend`。
3. 重启 web 容器：`docker compose restart web`。
4. 浏览器 Network 面板检查 `/api` 请求是否走了 5175 端口（Vite 代理生效）。

---

### Q10.4.2 pre-commit 拦截提交，提示 `! 前缀` 或 `teal-*` 净增量

**现象**：`git commit` 时被 `.githooks/pre-commit` 拦截，输出：

```
❌ Pre-commit 设计 token 守卫拦截：检测到禁用样式净增量
```

**原因**：新增了 Tailwind `!` 前缀类（如 `!p-0`、`!bg-brand-600`）或 `teal-*` 色阶类。

**解决方案**：
1. **`!` 前缀类**：改用 antd 组件默认 token，或在 `web/src/styles/index.css` 用带作用域的全局类覆盖。
2. **`teal-*` 色阶**：改为 `brand-*`（`tailwind.config.ts` 已定义 brand 色阶，hex 与 teal 相同）。
3. 卡片统一用 `rounded-xl` / `shadow-card`，不要各写 `!rounded-xl !shadow-[...]`。
4. 紧急情况可 `git commit --no-verify` 跳过，但需在 commit message 说明原因。
5. 详细规范见 [09-代码规范文档.md](09-代码规范文档.md#9.6-前端设计-token-与样式规范)。

---

### Q10.4.3 字体在不同分辨率下比例不一致

**现象**：1K / 2K / 4K 屏幕下文字大小看起来差异很大。

**原因**：使用了硬编码像素 `text-[12px]` 或 Tailwind 命名尺寸 `text-sm`。

**解决方案**：
统一使用 `text-fluid-*` 六级阶梯（定义在 `web/src/styles/index.css`）：

| CSS 类 | 用途 |
|--------|------|
| `text-fluid-xs` | 时间戳、设备码、Tag 内文字 |
| `text-fluid-sm` | 按钮文字、统计标签 |
| `text-fluid-base` | 正文、表格内容 |
| `text-fluid-lg` | 区块标题 |
| `text-fluid-xl` | 页面标题 |
| `text-fluid-stat` | 统计数字 |

- **禁止** `text-[11px]`、`text-[12px]` 等硬编码像素。
- **禁止**混用 `text-xs`/`text-sm` 与硬编码像素。
- 需新增级别时在 `styles/index.css` 扩展，不要在组件里写内联 `clamp()`。

---

### Q10.4.4 手机端横向滚动或侧栏撑爆

**现象**：手机访问页面出现横向滚动条，或侧栏宽度挤压内容。

**原因**：固定宽度未配响应式变体，或写死了 `SIDEBAR_WIDTH` 负 margin。

**解决方案**：
1. 固定宽度必须配响应式变体，改 mobile-first 写法：

```tsx
// ❌ 错误
<div className="w-64">

// ✅ 正确
<div className="w-full sm:w-52">
```

2. 尺寸用 `clamp(min, preferred, max)`，不要用裸 `vw` / `vh`。
3. 不要假设侧栏宽度恒定，`DashboardLayout` 已用 `useBreakpoint()` + `Drawer` 处理折叠。
4. 表格在小屏用 `scroll={{ x: ... }}` 允许横向滚动。

---

### Q10.4.5 状态标签颜色各页面不一致

**现象**：在线 / 离线状态在不同页面颜色、样式不统一。

**原因**：各 View 通过 `<Tag color="...">` 手动拼接内联 Tailwind 色阶类。

**解决方案**：
统一使用 `web/src/components/status-tag.tsx` 的 `<StatusTag />`：

```tsx
import { StatusTag } from '@/components/status-tag';

<StatusTag type="online" />
<StatusTag type="offline" />
<StatusTag type="active" />
<StatusTag type="pending" label="处理中" />
```

支持 `type`: `online` / `offline` / `active` / `inactive` / `bound` / `unbound` / `pending`，内部自动应用 `text-fluid-xs` 与规范圆点指示器。

## 10.5 WebSocket 与实时通信

### Q10.5.1 WebSocket 连接立即断开，返回 `1015` 或 `4401`

**现象**：前端或安卓建立 WebSocket 连接失败。

**原因**：
- 路径不对（项目只维护一个统一 WebSocket 入口）。
- 凭据缺失或失效。
- 走了多个业务 WebSocket URL（违反规范）。

**解决方案**：
1. 只使用统一 WebSocket 入口（见 [05-API接口文档.md](05-API接口文档.md) 的 WebSocket 协议章节）。
2. 通过 `type` 字段路由不同功能，不要新增多个 ws URL。
3. 检查 token / `X-Device-Code` 是否有效。
4. 错误码 `1015`（`REALTIME_UNAUTHORIZED`）→ 检查访问令牌和权限。

---

### Q10.5.2 实时命令报 `1011` / `1012` / `1013` / `1014`

**现象**：发送 WebSocket 命令后收到上述错误码。

**原因与解决方案**：

| 错误码 | 含义 | 解决方案 |
|--------|------|----------|
| `1011` | 实时命令必须是 JSON 文本消息 | 不要发二进制帧，用 JSON 文本帧 |
| `1012` | 实时命令必须是有效 JSON | 检查 JSON 编码 |
| `1013` | 实时命令类型不能为空 | 提供受支持的 `type` 字段 |
| `1014` | 不支持的实时命令 | 升级客户端或使用已发布的 `type` |

---

### Q10.5.3 ASR / TTS / LLM 上游服务报错

**现象**：语音对话过程中报 `1022` / `1027` / `1031` 等「上游服务暂不可用」。

**原因**：调用阿里云 DashScope / 第三方 LLM / TTS 上游失败。

**解决方案**：
1. 检查 `MULTIMODAL_API_KEY` / `DASHSCOPE_API_KEY` / `ALIYUN_TTS_API_KEY` 是否配置且有效。
2. 检查上游服务可用性（DashScope 控制台 / 第三方厂商状态页）。
3. 查看后端日志：

```bash
docker compose logs --tail 200 backend | Select-String -Pattern "ASR|TTS|LLM|upstream"
```

4. 持续失败时检查 `base_url` / `model` 配置是否过期。
5. 错误码详见 `backend/apps/error_codes/catalogue.py`。

---

### Q10.5.4 第三方机器人每轮都重新打开会话

**现象**：接入第三方 LLM / chatbot 后，每轮对话都新建第三方会话，上下文丢失。

**原因**：未正确复用第三方返回的上游会话 ID。

**解决方案**（详见 `wiki/第三方机器人上下文集成指南.md`）：
1. **方案 A**（先创建会话再发消息）：必须配置响应 `extract` 和创建会话步骤的 `skipWhenVariableExists`，避免每轮重新打开第三方会话。
2. **方案 B**（单个 chat 接口自动创建 / 续接）：必须用请求体模板回传第三方返回的 `sessionId`，首轮需要 JSON `null` 时使用 `nullWhenMissingVariables`，**不要长期写死 `sessionId: null`**。
3. 发给第三方的上游会话 ID 必须来自第三方 API 响应，按该厂商配置的字段 / 路径保存和复用。**不要**把安卓、HTTP 语音、WebSocket 的本地 `sessionId` 当成第三方 `chat_id` / `sessionId` 发送。
4. 新增第三方集成时至少补一个两轮回归测试：首轮模拟第三方返回上游会话 ID，第二轮断言请求第三方时复用同一个 ID。

## 10.6 Celery 异步任务

### Q10.6.1 异步任务不执行

**现象**：触发异步任务后无响应，`celery_worker` 日志无消费记录。

**原因**：
- worker 未启动或未注册任务。
- broker（Redis）不可达。
- 任务序列化失败。

**解决方案**：
1. 确认 worker 健康：`docker compose ps celery_worker`。
2. 查看已注册任务：

```bash
docker compose exec celery_worker celery -A config inspect registered
```

3. 查看 broker：`docker compose exec redis redis-cli -n 1 LLEN celery`。
4. 确认 `CELERY_BROKER_URL` 指向可达的 Redis（默认 `redis://redis:6379/1`）。
5. 检查任务序列化：`CELERY_ACCEPT_CONTENT = ['json']`，任务参数必须可 JSON 序列化。

---

### Q10.6.2 周期任务不触发

**现象**：`celery_beat` 已启动，但周期任务不执行。

**原因**：
- beat 未使用 `DatabaseScheduler`。
- 周期任务在 Admin 中被禁用。
- `seed_operations_periodic_tasks` 未执行。

**解决方案**：
1. 确认 beat 启动命令含 `--scheduler django_celery_beat.schedulers:DatabaseScheduler`。
2. 登录 Django Admin →「周期任务」，确认任务 `enabled=True` 且 `crontab` / `interval` 配置正确。
3. 手动重跑种子任务：

```bash
docker compose exec backend python manage.py seed_operations_periodic_tasks
```

4. 查看 beat 日志确认 `Scheduler: Sending due task`。

---

### Q10.6.3 worker 与 backend 代码不一致

**现象**：backend 已更新业务逻辑，但异步任务行为仍是旧的。

**原因**：仅重建了 backend，未重建 `celery_worker` / `celery_beat`（三者共用同一镜像）。

**解决方案**：
后端代码变更必须一起重建：

```bash
docker compose up -d --build backend celery_worker celery_beat
```

## 10.7 GitNexus 与 Git Hooks

### Q10.7.1 commit / merge 后 GitNexus 钩子报错

**现象**：Git 操作完成后输出 GitNexus 警告或错误。

**原因**：`.githooks/` 钩子触发 `analyze --index-only` 失败。

**解决方案**：
1. **不影响 Git 操作**：自动更新失败不会回滚已完成的 Git 操作。
2. 临时关闭：`$env:GITNEXUS_AUTO_UPDATE=0`（PowerShell）。
3. 检查状态：`node .gitnexus/run.cjs status`。
4. 手动重建索引：`node .gitnexus/run.cjs analyze`。
5. 若无 `.gitnexus/run.cjs`：`npx gitnexus analyze`（npm 11 崩溃则 `npm i -g gitnexus`）。

---

### Q10.7.2 GitNexus 索引过期，工具结果不准

**现象**：`query` / `context` / `impact` 返回的结果与实际代码不符。

**原因**：图谱索引未跟上最新代码变更。

**解决方案**：
1. 手动重建：`node .gitnexus/run.cjs analyze`。
2. 确认 `git config core.hooksPath .githooks` 已配置（否则 commit 后不会自动更新）。
3. 降级方案：图谱未覆盖时回退到 Grep / Glob / Read 搜索源码。

---

### Q10.7.3 `impact` 报告 HIGH / CRITICAL 风险

**现象**：修改某符号前运行 `impact`，返回 HIGH 或 CRITICAL。

**原因**：该符号被大量调用者依赖，修改影响面大。

**解决方案**：
1. **必须警告用户后再继续**，不要默默修改。
2. 评估是否能用更小 diff 的方式实现（如新增重载而非改签名）。
3. 必须修改时，先用 `context` 拉取所有调用者，逐个评估兼容性。
4. 重命名用 `rename` 工具（理解调用图），**不要** find-and-replace。
5. 提交前 `detect_changes()` 验证变更只影响预期符号。

## 10.8 部署

### Q10.8.1 HTTPS 访问报证书错误

**现象**：浏览器提示证书无效或过期。

**原因**：TLS 证书过期，或 `Caddyfile` 指向的证书路径不对。

**解决方案**：
1. 确认 `${TLS_CERT_DIR}`（默认 `./26179784_conai.chat_other`）下有 `conai.chat.pem` 和 `conai.chat.key`。
2. 检查证书有效期：`openssl x509 -in conai.chat.pem -noout -dates`。
3. 替换新证书后 Caddy 会自动热加载，无需重启。
4. 或改用 Let's Encrypt：`Caddyfile` 改为 `tls conai.chat`，让 Caddy 自动申请。

---

### Q10.8.2 部署后安卓设备拉取配置失败

**现象**：生产部署后，安卓设备无法拉取运行时配置或发起对话。

**原因**：
- 设备未登记或未绑定公司 / 智能体。
- `X-Device-Code` 未透传。
- WebSocket 在生产域名下不通。

**解决方案**：
1. 确认设备已在后台 `/api/v1/devices/` 登记，且 `is_enabled=True`。
2. 确认设备已绑定公司与可用智能体。
3. 确认 Caddy 反向代理了 `/ws` 路径到 backend（见 [08-部署流程说明.md](08-部署流程说明.md#8.4-caddy-反向代理配置)）。
4. 确认安卓设备上报不应覆盖后台维护的设备名称。
5. 用 `wiki/android-device-runtime-simulator.html` 模拟设备验证。

---

### Q10.8.3 默认 `admin` 账号被入侵

**现象**：生产环境仍用默认密码 `admin123456`。

**原因**：backend 启动命令会自动创建默认超管（仅当不存在），未及时改密。

**解决方案**：
1. **首次部署必须立即改密**：

```bash
docker compose exec backend python manage.py changepassword admin
```

2. 或登录 Django Admin 修改。
3. 生产环境建议禁用该账号或删除，改用最小权限账号。

## 10.9 错误码速查表

完整错误码定义见 `backend/apps/error_codes/catalogue.py`。实时错误码格式为 4 位字符串（`1001`–`1035`），部分有 legacy HTTP 状态码（`44001` 等）。

### 10.9.1 设备运行时（1001–1009）

| 码 | key | 含义 | 建议 |
|----|-----|------|------|
| 1001 | `DEVICE_CODE_REQUIRED` | 设备码不能为空 | 提供已登记设备码 |
| 1002 | `DEVICE_NOT_REGISTERED` | 设备未登记 | 后台登记设备 |
| 1003 | `DEVICE_CODE_DUPLICATED` | 设备码重复绑定 | 平台管理员清理重复 |
| 1004 | `DEVICE_TENANT_UNBOUND` | 设备未绑定公司 | 绑定有效公司 |
| 1005 | `DEVICE_TENANT_DISABLED` | 公司已停用 | 恢复公司或换绑 |
| 1006 | `DEVICE_DISABLED` | 设备已停用 | 启用设备 |
| 1007 | `DEVICE_EXPIRED` | 设备授权已过期 | 续期授权 |
| 1008 | `DEVICE_AGENT_UNBOUND` | 未绑定可用智能体 | 绑定并启用智能体 |
| 1009 | `DEVICE_APPLICATION_INACTIVE` | 绑定应用未启用 | 启用应用 |

### 10.9.2 实时协议（1010–1018）

| 码 | key | 含义 |
|----|-----|------|
| 1010 | `REALTIME_RUNTIME_CONFIG_SUBSCRIPTION_FAILED` | 运行时配置订阅失败 |
| 1011 | `REALTIME_MESSAGE_REQUIRED` | 实时命令必须是 JSON 文本 |
| 1012 | `REALTIME_INVALID_JSON` | 实时命令必须是有效 JSON |
| 1013 | `REALTIME_COMMAND_TYPE_REQUIRED` | 命令类型不能为空 |
| 1014 | `REALTIME_UNKNOWN_COMMAND` | 不支持的实时命令 |
| 1015 | `REALTIME_UNAUTHORIZED` | 实时会话未授权 |
| 1016 | `REALTIME_DEVICE_NOT_AVAILABLE` | 设备不可用 |
| 1017 | `REALTIME_DEVICE_STATUS_NOT_STARTED` | 设备状态会话尚未启动 |
| 1018 | `REALTIME_VOICE_NOT_AVAILABLE` | 音色不可用 |

### 10.9.3 语音与大模型（1019–1032）

| 码 | key | 含义 |
|----|-----|------|
| 1019 | `ASR_UNAUTHORIZED` | ASR 会话未授权 |
| 1020 | `ASR_NOT_READY` | ASR 服务未就绪 |
| 1021 | `ASR_SESSION_NOT_STARTED` | ASR 会话尚未启动 |
| 1022 | `ASR_UPSTREAM_ERROR` | ASR 上游不可用 |
| 1023 | `TTS_UNAUTHORIZED` | TTS 会话未授权 |
| 1024 | `TTS_NOT_READY` | TTS 服务未就绪 |
| 1025 | `TTS_VOICE_NOT_AVAILABLE` | TTS 音色不可用 |
| 1026 | `TTS_SESSION_NOT_STARTED` | TTS 会话尚未启动 |
| 1027 | `TTS_UPSTREAM_ERROR` | TTS 上游不可用 |
| 1028 | `LLM_DEVICE_CODE_REQUIRED` | 设备码不能为空 |
| 1029 | `LLM_QUESTION_REQUIRED` | 问题内容不能为空 |
| 1030 | `LLM_SESSION_NOT_STARTED` | LLM 会话尚未启动 |
| 1031 | `LLM_UPSTREAM_ERROR` | LLM 上游不可用 |
| 1032 | `LLM_EMPTY_RESPONSE` | LLM 未返回有效回复 |

### 10.9.4 智能体与内部错误（1033–1035）

| 码 | key | 含义 |
|----|-----|------|
| 1033 | `AGENT_SESSION_NOT_STARTED` | 智能体会话尚未启动 |
| 1034 | `AGENT_ASR_SESSION_NOT_STARTED` | 智能体 ASR 会话尚未启动 |
| 1035 | `INTERNAL_ERROR` | 服务内部错误 |

> 上游不可用类错误（`1022` / `1027` / `1031`）先稍后重试，持续失败时检查服务端日志和上游配置。`1035` 持续失败时把关联 ID（`x-request-id` / `x-trace-id`）提供给平台管理员。

## 10.10 排查通用思路

1. **看健康状态**：`docker compose ps`，先确认服务是否 healthy。
2. **看日志**：`docker compose logs --tail 200 <service>`，按服务名过滤。
3. **看请求 ID**：浏览器 Network 面板取 `x-request-id` / `x-trace-id`，在日志中按 ID 检索完整链路。
4. **看错误码**：对照 `backend/apps/error_codes/catalogue.py` 查含义与建议动作。
5. **看图谱**：用 GitNexus `query` / `context` / `impact` 理解代码调用关系，避免盲改。
6. **看文档**：本套文档的 [04-数据流程图.md](04-数据流程图.md) 与 [05-API接口文档.md](05-API接口文档.md) 通常是定位数据流问题的关键。
7. **最小复现**：用 `wiki/android-device-runtime-simulator.html` 模拟设备，隔离前端 / 安卓因素。
