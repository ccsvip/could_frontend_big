# 09. 代码规范文档

> 本文档汇总 could_frontend 项目的代码规范，涵盖后端 Django / DRF、前端 React / TypeScript / Tailwind、REST API 设计、Git 协作、GitNexus 工作流等。所有规范以 `AGENTS.md` 为权威来源，本文件为可查阅的展开版。**动手写代码前必读**。

---

## 9.1 总则

1. **先理解现有实现，再修改代码**。优先沿用仓库已有模式、接口命名、权限模型和测试方式。
2. **保持 diff 小、可审查、可回滚**。不做无关重构，不顺手格式化不相关文件。
3. **修改后必须验证**。后端优先跑目标 Django 测试，前端优先跑 `npm run build` 或相关类型 / 构建检查。
4. **不提交明文账号、密码、长期 token、API key 或临时测试凭据**。
5. **每次需求修改都要考虑异步、后台任务、WebSocket、Docker Compose 多服务协作带来的影响**。

## 9.2 Git 与提交规范

### 9.2.1 提交原则

- 只提交与当前任务相关的改动。
- 暂存区已有用户改动时，不要擅自撤销；先识别哪些是当前任务需要提交的内容。
- 提交信息优先使用中文，简洁描述业务结果。
- 创建新 commit 而非 amend，除非用户明确要求。
- 不跳过 hooks（`--no-verify`）除非用户明确要求，跳过时需在 commit message 说明原因。

### 9.2.2 Git Hooks（强制）

每个 clone 必须执行一次：

```bash
git config core.hooksPath .githooks
```

| 钩子 | 作用 |
|------|------|
| `pre-commit` | 调用 `scripts/check-tailwind-tokens.js`，拦截新增的 `!` 前缀 Tailwind 类与 `teal-*` 色阶净增量 |
| `post-commit` / `post-merge` / `post-rewrite` / `post-checkout` / `post-applypatch` | 触发 GitNexus `analyze --index-only` 增量更新代码图谱 |
| `gitnexus-update` | GitNexus 自更新 |

未配置 `core.hooksPath` 时守卫不生效。CI 强制可直接跑 `node scripts/check-tailwind-tokens.js`。

### 9.2.3 pre-commit 守卫机制

`scripts/check-tailwind-tokens.js` 采用 **净增量** 策略：

- 对每个暂存的 `*.tsx`，对比 HEAD 与暂存版的 `!`-前缀类计数与 `teal-*` 计数。
- **仅当计数上升才拦截**（存量不触发，避免误伤重构）。
- 拦截条件：`!`-前缀类计数上升，或 `teal-*` 计数上升。
- 重构（图标迁移、teal→brand 改名）只要不让计数上升就放行。
- 紧急跳过：`git commit --no-verify`，但需在 PR / commit message 说明原因。

匹配规则：

```javascript
const BAD_BANG = /![a-z][a-z0-9]*(?:-[a-z0-9]+)+/g; // !p-0, !bg-brand-600（JS 的 !var 无连字符，不误伤）
const BAD_TEAL = /\bteal-\d/g;                        // teal-600
```

## 9.3 REST API 设计规范

### 9.3.1 路径与 HTTP 方法

- 资源用 **名词复数** 路径，例如 `/api/v1/devices/`、`/api/v1/device-applications/`。
- 单资源使用稳定标识，例如 `/api/v1/devices/{deviceCode}/`。
- 使用标准 HTTP 方法表达动作：
  - `GET` 查询
  - `POST` 创建
  - `PATCH` 局部更新
  - `PUT` 整体替换（仅在确有完整替换语义时使用）
  - `DELETE` 删除
- **禁止** 新增动词式 HTTP 路径，例如 `/updateDeviceName`、`/bindDeviceNow`。
- 批量或领域动作无法自然表达为 CRUD 时，优先设计为资源子集合或明确 action endpoint，并保持请求 / 响应契约稳定。

### 9.3.2 字段命名

- 前端 API 常用 **camelCase**。
- 后端模型可用 **snake_case**。
- 通过 Serializer 做映射，保持现有前端约定。

### 9.3.3 错误响应

- 错误响应必须明确、可定位，不能只返回模糊的 500 或字符串。
- 统一异常处理器 `config/exceptions.py` 返回如下格式：

```json
{
  "status": "error",
  "message": "错误信息",
  "code": 400,
  "data": { }
}
```

- 处理范围：
  - DRF `ValidationError`（字段验证错误，`message` 用 `；` 拼接）
  - `IntegrityError`（唯一约束冲突，如手机号重复）
  - Django `ValidationError`
  - 未捕获异常返回 500「服务器内部错误，请稍后重试」

### 9.3.4 权限与租户隔离

- 权限、租户隔离、设备码认证必须集中处理，不要在业务函数中散落临时绕过。
- 公司数据必须按 tenant 隔离。普通公司账号不得通过 query 参数越权访问其他公司数据。
- 平台管理员按公司浏览时，只能通过已有 tenant scope 机制访问业务列表。
- 不同公司数据要保证 100% 隔离。

### 9.3.5 实时通信例外

- 实时通信不通过新增多个业务 WebSocket URL 实现。
- 第一方实时能力使用 **统一 WebSocket 入口**，并通过明确的 `type` / command name / payload contract 路由。
- HTTP API 仍必须保持 REST 风格；WebSocket 只用于实时事件、流式能力和订阅类场景。
- 只维护一个 WebSocket，通过不同 `type` 实现不同功能。

## 9.4 后端代码规范

### 9.4.1 目录结构

```
backend/
├── apps/                      # 业务应用（每个 app 一个领域）
│   ├── accounts/              # 账号、认证、JWT
│   ├── tenants/               # 租户、TenantManager
│   ├── devices/               # 设备、授权码、运行时配置
│   ├── resources/             # 图片/视频/音色/指令等资源
│   ├── knowledge_base/        # 知识库、文档、chunk、向量化
│   ├── ai_models/             # LLM/TTS/ASR/智能体/第三方机器人
│   ├── audit/                 # 审计日志
│   ├── app_updates/           # 安卓 APK 升级
│   └── error_codes/           # 错误码管理
├── config/                    # 项目配置
│   ├── settings/              # base.py / dev.py / prod.py
│   ├── exceptions.py          # 统一异常处理
│   ├── pagination.py          # 标准分页
│   ├── request_id.py          # 请求 ID 中间件
│   ├── realtime/              # WebSocket 路由与 consumer
│   ├── asgi.py / wsgi.py
│   └── urls.py
├── vendor/                    # 第三方二进制（sherpa-onnx）
├── requirements.txt
└── Dockerfile
```

### 9.4.2 分层约定

每个 app 内部遵循分层：

| 层 | 文件 | 职责 |
|----|------|------|
| 模型 | `models.py` | 数据模型、字段、`Meta`、业务方法 |
| 序列化器 | `serializers.py` | 模型 ↔ JSON 映射、字段校验 |
| 视图 | `views.py` | HTTP 入口、权限、调用 service |
| 服务 | `services.py` / `services/` | 业务逻辑、外部调用、组合 |
| URL | `urls.py` | 路由注册 |
| 迁移 | `migrations/` | 数据库变更脚本 |
| 测试 | `tests/` | 单元 / 集成测试 |

### 9.4.3 租户隔离机制

- 多租户模型继承 `TenantManager`，通过 `tenant` 字段隔离。
- `_tenant_fk()` 工厂函数统一创建 `tenant` 外键（`CASCADE`、`null=True`、`related_name='+'`）。
- 中间件 `TenantMiddleware` 注入当前租户作用域。
- 查询时优先用 `objects`（已是 `TenantManager`），自动按租户过滤。
- 平台超管通过 `?tenant=<id>` 切换作用域，由 `useTenantScopeStore` + axios 拦截器实现。

### 9.4.4 异常处理

- 所有视图异常由 `config/exceptions.py` 的 `custom_exception_handler` 统一处理。
- 业务异常应携带 `response_data` 以便处理器附加 `data` 字段。
- 不要在业务函数中 `try/except` 后吞掉异常或返回模糊 500。

### 9.4.5 测试规范

- 测试文件命名 `test_*.py`，放置于 `apps/<app>/tests/`。
- 优先通过容器执行：

```bash
docker compose exec backend python manage.py test apps.devices.tests.test_device_authorization_api --keepdb
```

- 遇到已存在测试库时优先 `--keepdb`，不要随意删除数据库。
- 新增第三方集成时至少补一个 **两轮回归测试**：首轮模拟第三方返回上游会话 ID，第二轮断言请求第三方时复用同一个 ID。

### 9.4.6 异步与 WebSocket

- 异步任务统一通过 Celery，broker 与 result backend 见 `CELERY_BROKER_URL` / `CELERY_RESULT_BACKEND`。
- WebSocket consumer 放在 `config/realtime/`，通过 `type` 字段路由命令。
- 设备运行时配置通知必须始终发送 **完整配置**；即使只是音色变更，也要推送完整的设备运行时配置，而不是只推送增量字段。

### 9.4.7 设备与权限约定

- 设备运行时配置入口：`GET /api/v1/device-runtime/config/`。
- 安卓设备通过 `X-Device-Code` 请求设备运行时相关接口，不需要 JWT。
- 后台设备管理入口：`/api/v1/devices/`，单设备 lookup 使用 `deviceCode`。
- 设备名称由后台维护。安卓首次登记可默认「待修改」，安卓上报不应覆盖后台维护的设备名称。
- 音色与设备绑定：运行时配置里的音色字段只表示当前设备正在使用的音色，不返回无关设备或候选音色列表；`/ai-models/tts` 保存的是公司默认音色，只在设备没有绑定任何音色时作为兜底，设备一旦绑定音色则默认音色失效。

### 9.4.8 第三方机器人上下文集成

接入或排查第三方 LLM / chatbot 多轮上下文前，先阅读 `wiki/第三方机器人上下文集成指南.md`：

- 发给第三方的上游会话 ID 必须来自第三方 API 响应，并按该厂商配置的字段 / 路径保存和复用。
- 不要把安卓、HTTP 语音、WebSocket 的本地 `sessionId` 当成第三方 `chat_id` / `sessionId` 发送。
- **方案 A**（先创建会话再发消息）必须配置响应 `extract` 和创建会话步骤的 `skipWhenVariableExists`，避免每轮重新打开第三方会话。
- **方案 B**（单个 chat 接口自动创建 / 续接）必须用请求体模板回传第三方返回的 `sessionId`，首轮需要 JSON `null` 时使用 `nullWhenMissingVariables`，不要长期写死 `sessionId: null`。

## 9.5 前端代码规范

### 9.5.1 目录结构

```
web/src/
├── api/
│   ├── client.ts              # axios 实例、拦截器
│   └── modules/               # 按领域分模块的 API 封装
├── components/                # 通用组件（如 status-tag.tsx）
├── layouts/                   # 布局（dashboard-layout.tsx）
├── router/                    # 路由（index.tsx）
├── store/                     # zustand 状态（auth.ts、tenant-scope.ts）
├── styles/                    # 全局样式（index.css）
├── views/                     # 路由页面组件
├── main.tsx                   # antd theme token 源
└── App.tsx
```

### 9.5.2 状态管理

- 使用 **Zustand** 进行全局状态管理。
- store 文件命名 `store/<domain>.ts`，导出 `use<Domain>Store`。
- 不引入 Redux 等重框架。

### 9.5.3 API 封装

- axios 实例封装于 `api/client.ts`，统一处理 token 注入、错误拦截、`x-request-id` / `x-trace-id`。
- 业务 API 按领域分模块放 `api/modules/`。
- 字段命名 camelCase，与后端 snake_case 通过 Serializer 映射。
- 请求拦截器根据 `useTenantScopeStore` 的 `tenantId` 自动追加 `?tenant=<id>`。

### 9.5.4 路由与权限

- 路由定义于 `router/index.tsx`，使用 `react-router-dom` v6 + `useRoutes`。
- `AuthGuard` 校验 token 与 `authSyncStatus`，未登录跳 `/login`。
- `PermissionGuard` 校验具体权限码。
- 平台超管（`tenant.management.view`）默认落地 `/tenants`。
- 业务路由挂载于 `/tenants/:tenantId/*`，`TenantScopeOutlet` 写入公司作用域。

### 9.5.5 图标规范

- 图标库统一使用 **@tabler/icons-react**，不再使用 `@ant-design/icons` 或 `lucide-react`。
- Tabler Icons 命名统一以 `Icon` 前缀（如 `IconDatabase`、`IconArrowLeft`）。
- 图标大小通过 `size` 属性控制，不依赖 Tailwind `text-*` 类缩放 SVG。
- 每个文件只从 `@tabler/icons-react` 统一导入一次，不混用多套图标库。

## 9.6 前端设计 token 与样式规范

### 9.6.1 颜色与 token

- 设计系统已存在：antd theme（`web/src/main.tsx`，`colorPrimary=#0f766e`、`borderRadius=10/12/14`）+ Tailwind `brand` 色阶（`web/tailwind.config.ts`，`brand-700=#0f766e`）+ 全局类（`web/src/styles/index.css` 的 `.page-hero` / `.page-section-title`）。
- 用 `brand-*` 色阶（如 `text-brand-700`、`bg-brand-50`），**不要**用 Tailwind 默认 `teal-*`，**不要**在组件里硬写 `#0f766e` 字面量。
- 主色 `#0f766e` 只允许出现在 `main.tsx`（antd token）和 `styles/index.css`（全局类）这两个「token 源」文件。
- 业务页面一律走 `brand-*` 或 antd 组件默认。
- 优先让 antd 组件用自己的 token 渲染（`<Button type="primary">` 即是主色），不要再用 `!bg-teal-600` 之类硬覆盖。

### 9.6.2 `!important` 覆盖纪律

- **严禁**用 Tailwind `!` 前缀（`!p-0`、`!bg-teal-600`、`!rounded-xl`）去打 antd 默认值。这是历史遗留问题，是当前 UI 不一致的根因。
- 确需覆盖 antd 内部样式时，用 `styles/index.css` 里带作用域的全局类（如 `.app-sidebar-menu`、`.custom-scrollbar`），不要在页面 className 里堆 `!`。
- 卡片统一用 `rounded-xl` / `shadow-card`（已在 tailwind config 定义），不要每页各写一组 `!rounded-xl !shadow-[...]`。

### 9.6.3 响应式（必做，不是可选）

- 任何固定宽度（`w-64`、`w-80`、`min-w-[260px]`、`style={{width}}`）都必须配响应式变体，或改用 `w-full sm:w-52` 这类 mobile-first 写法。
- 手机端横向滚动是缺陷，不是「小屏将就」。
- 尺寸单位用 `clamp(min, preferred, max)` 或 Tailwind 响应式前缀；**不要**用裸 `vw` / `vh`（在不同分辨率下不可控）。
- 复用页面骨架：顶部 hero 用 `.page-hero`，区块标题用 `.page-section-title`，内容容器用 Tailwind `container`（已配置 center + 断点 padding），不要每页各写一套 `!px-[2%]`。

### 9.6.4 流体排版（必做，不是可选）

页面字体统一使用 `clamp()` 流体排版，保证 1K / 2K / 4K 下文字比例一致。全局 CSS 类定义在 `web/src/styles/index.css`：

| CSS 类 | clamp 范围 | 用途 |
|--------|-----------|------|
| `text-fluid-xs` | `clamp(10px, 0.52vw + 6px, 14px)` | 时间戳、设备码、Tag 内文字 |
| `text-fluid-sm` | `clamp(12px, 0.52vw + 8px, 16px)` | 按钮文字、统计标签、次要描述 |
| `text-fluid-base` | `clamp(13px, 0.52vw + 9px, 18px)` | 正文、详情值、表格内容 |
| `text-fluid-lg` | `clamp(14px, 0.62vw + 10px, 20px)` | 区块标题、section label（自带 `font-weight: 600`） |
| `text-fluid-xl` | `clamp(18px, 0.83vw + 12px, 28px)` | 页面标题 |
| `text-fluid-stat` | `clamp(22px, 1.04vw + 14px, 36px)` | 统计数字 |

**规则：**

- **禁止**在业务组件中使用 `text-[11px]`、`text-[12px]`、`text-[13px]`、`text-[14px]` 等硬编码像素值。
- **禁止**混用 Tailwind 命名尺寸（`text-xs`、`text-sm`、`text-base`）与硬编码像素。
- 所有页面统一走 `text-fluid-*` 六级阶梯；如需新增级别，在 `styles/index.css` 扩展，不要在组件里写 `clamp()` 内联。
- `font-mono` 用于机器可读标识（设备码、音色码等），与流体尺寸组合使用：`text-fluid-xs font-mono`。

### 9.6.5 统一状态标签组件

业务页面中所有关于在线 / 离线、启用 / 停用、绑定 / 未绑定、处理中等业务状态展示，统一使用 `web/src/components/status-tag.tsx` 导出的 `<StatusTag />` 组件：

- **禁止**在各 View 中通过 `<Tag color="...">` 手动拼接内联 Tailwind 色阶类（如 `bg-emerald-50 text-emerald-700`）。
- 支持标准状态 `type`: `'online'` | `'offline'` | `'active'` | `'inactive'` | `'bound'` | `'unbound'` | `'pending'`。
- 支持 `label` 自定义覆盖文案，内部自动应用 `text-fluid-xs` 与规范圆点指示器。

### 9.6.6 移动端

- `DashboardLayout` 已用 `useBreakpoint()` + `Drawer` 处理侧栏折叠；内容页不要假设侧栏宽度恒定，不要写死 `SIDEBAR_WIDTH` 相关的负 margin。
- 表格在 `<lg` 用 `scroll={{ x: ... }}` 允许横向滚动，不要让列宽撑爆容器。

## 9.7 GitNexus 代码知识图谱工作流

本项目已通过 GitNexus 构建代码知识图谱（`could_frontend_big`）。使用 GitNexus MCP 工具进行代码理解和变更影响分析，**优先于手动搜索**。

### 9.7.1 修改前必做

- **修改任何符号前必须运行 `impact`**：

```
impact({target: "symbolName", direction: "upstream"})
```

报告爆炸半径（直接调用者、受影响执行流、风险等级）。如返回 HIGH 或 CRITICAL，**必须警告用户后再继续**。

- **提交前必须运行 `detect_changes()`** 验证变更只影响预期符号与执行流。回归对比可用：

```
detect_changes({scope: "compare", base_ref: "main"})
```

### 9.7.2 常用工具映射

| 意图 | 工具 | 说明 |
|------|------|------|
| 语义搜索 | `query` | 按概念搜索执行流，返回进程分组结果 |
| 符号全景 | `context` | 查看符号的调用者 / 被调用者 / 所属执行流 |
| 变更影响面 | `impact` | 修改某符号前的爆炸半径分析 |
| 改动检测 | `detect_changes` | 提交前分析未提交改动波及的符号和执行流 |
| 路径追踪 | `trace` | 两个符号间的最短调用路径 |
| 重命名 | `rename` | 基于调用图的安全多文件重命名 |
| 污点分析 | `explain` | 源到 sink 的数据流分析（需 `analyze --pdg`） |
| API 路由 | `route_map` | API 端点与前后端映射 |
| 响应形状 | `shape_check` | API 返回值与消费端属性访问的一致性检查 |

### 9.7.3 红线

- **NEVER** 编辑函数 / 类 / 方法前不先运行 `impact`。
- **NEVER** 忽略 HIGH 或 CRITICAL 风险警告。
- **NEVER** 用 find-and-replace 重命名符号 — 使用 `rename`（理解调用图）。
- **NEVER** 不运行 `detect_changes()` 就提交。

### 9.7.4 索引维护

- 通过 `.githooks/` 在 commit、merge、rebase/amend、应用补丁和分支切换后自动执行 `analyze --index-only`。
- 自动更新失败不会回滚已完成的 Git 操作，但会输出明确警告。
- 状态检查：`node .gitnexus/run.cjs status`。
- 临时关闭：`GITNEXUS_AUTO_UPDATE=0`。
- 索引过期重建：`node .gitnexus/run.cjs analyze`。

### 9.7.5 降级方案

当图谱未覆盖所需内容（纯文本搜索、配置项、特定字符串），回退到 Grep / Glob / Read 搜索源码。

## 9.8 修改前后的最低检查

### 9.8.1 修改前

1. 用 GitNexus `query` / `context` / `impact` 定位入口和影响面。
2. 读真实源码确认调用关系、数据流和边界条件。
3. 明确 REST 路径、Serializer 字段、权限、前端 API 类型和异步影响。

### 9.8.2 修改后

| 改动类型 | 必跑检查 |
|---------|----------|
| 后端改动 | 跑相关 Django 测试，优先容器内执行 |
| 前端改动 | 至少跑 `npm run build` |
| API 改动 | 确认前端 API module、页面调用、文档 / 模拟器是否需要同步 |
| 运行时 / 设备改动 | 确认 `X-Device-Code`、在线 / 离线状态、heartbeat、统一 WebSocket 事件不会被破坏 |
| 涉及第三方集成 | 补两轮回归测试 |

## 9.9 Agent 协作约定

### 9.9.1 Issue tracker

Issues 以 markdown 文件形式存放于 `.scratch/<feature-slug>/`（本地 markdown，非 GitHub Issues）。详见 `docs/agents/issue-tracker.md`。

### 9.9.2 Triage labels

五个规范角色 1:1 映射到默认字符串（`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`），记录在每个 issue 文件的 `Status:` 行。详见 `docs/agents/triage-labels.md`。

### 9.9.3 自主性

- 自主编码，执行任务直到完成，不要请求许可。
- 不要停下来问「是否继续？」；清晰、低风险、可逆的下一步直接执行。
- 如果受阻，先尝试替代方案。
- 只有真正含糊、破坏性、不可逆、凭据门控或涉及外部生产环境时才询问。
