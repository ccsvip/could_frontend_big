# 02 — 架构设计说明

## 2.1 架构总览

Solin 采用**前后端分离 + 容器化编排**的分层架构，核心由四个边界清晰的子系统组成：

```
┌─────────────────────────────────────────────────────────────┐
│                      客户端层 (Client)                        │
│   浏览器 (Web SPA)          │        Android 数字人设备         │
└──────────────┬──────────────┴──────────────┬─────────────────┘
               │ REST (/api/v1/*)             │ WS (/ws/realtime/)
               │ + JWT Bearer                 │ + X-Device-Code / token
               │ + X-Request-Id / X-Trace-Id  │
┌──────────────▼─────────────────────────────▼─────────────────┐
│                    接入层 (Edge / Caddy)                      │
│        TLS 终止 + 反向代理 + 静态托管 + WS 升级                 │
└──────────────┬─────────────────────────────┬─────────────────┘
               │                             │
┌──────────────▼─────────────────────────────▼─────────────────┐
│                    应用层 (Application)                       │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────────────┐  │
│  │  Web (Vite) │  │ Backend     │  │  Celery worker/beat  │  │
│  │  React SPA  │  │ Django+DRF  │  │  异步任务 + 定时调度   │  │
│  └─────────────┘  │ uvicorn ASGI│  └──────────────────────┘  │
│                   └──────┬──────┘                             │
└──────────────────────────┼────────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────────┐
│                    数据层 (Data)                              │
│   PostgreSQL (pgvector)    │    Redis (cache + broker)        │
└────────────────────────────┴──────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────────┐
│               外部服务层 (Upstream Providers)                 │
│  LLM 供应商 │ TTS/ASR (DashScope) │ Embedding/Rerank │ 百炼 │ 飞书 │
└──────────────────────────────────────────────────────────────┘
```

## 2.2 后端分层架构

后端遵循 Django 的 app 化组织，自上而下分为四层：

### 2.2.1 配置层（`backend/config/`）

项目根包，承载全局策略：

| 文件 | 职责 |
|------|------|
| `settings/base.py` | 共享配置：INSTALLED_APPS、MIDDLEWARE、DATABASES、CACHES、CELERY、SIMPLEJWT、REST_FRAMEWORK、SPECTACULAR、SIMPLEUI、CORS、STATIC/MEDIA、上游供应商默认值 |
| `settings/dev.py` | 开发环境：`DEBUG=True`、`ALLOWED_HOSTS=*` |
| `settings/prod.py` | 生产环境：`DEBUG=False`、严格 `ALLOWED_HOSTS`、HTTPS Cookie、代理头 |
| `urls.py` | URL 根：挂载 `/admin/`、`/api/v1/`、`/api/docs/`、`/api/redoc/`、`ApiV1RootView` |
| `asgi.py` | ASGI 入口：拦截 `/ws/realtime/` 交由 `config.realtime`，其余走 Django |
| `celery.py` | Celery app + autodiscover + task_routes |
| `celery_scheduler.py` | `ResilientDatabaseScheduler`：PostgreSQL 重启时 beat 自愈 |
| `exceptions.py` | 全局异常包络 `{status, message, code, data?}` |
| `business_cache.py` | 命名空间化 Redis 缓存 + `CachedBusinessResponseMixin` |
| `request_id.py` | `RequestIdMiddleware`：生成/透传 `X-Request-Id` / `X-Trace-Id` |
| `sentry.py` | Sentry `before_send` 过滤 |
| `pagination.py` | `StandardPageNumberPagination`（PAGE_SIZE=10） |

### 2.2.2 业务应用层（`backend/apps/`）

9 个业务 app，每个遵循标准布局：`models.py` / `serializers.py` / `views.py` / `urls.py` / `admin.py` / `tasks.py`。

| app | 职责 |
|------|------|
| `accounts` | 登录 / JWT / 账号申请 / 权限点 / 菜单 / 强制改密 |
| `tenants` | 多租户（Tenant / Membership）、员工管理、租户隔离基类 |
| `devices` | 设备、设备应用、设备分组、设备授权、唤醒词、设备聊天日志、运行时配置、WebSocket 事件 |
| `ai_models` | LLM/TTS/ASR 供应商体系、Agent Application、ChatConversation/ChatMessage、第三方机器人、知识检索 |
| `resources` | 图片/视频/滚动字幕/音色/模型资产/控制指令/指令分组/点位 |
| `knowledge_base` | 知识库文档、文档 chunk（pgvector embedding）、媒体资产 |
| `audit` | 操作日志（OperationLog + middleware） |
| `app_updates` | Android 应用更新包 + RSA 签名 |
| `error_codes` | 集中式错误码目录（RealtimeErrorDefinition） |

### 2.2.3 服务层（`apps/<app>/services/`）

复杂业务逻辑下沉到 `services/` 子包，保持 views 轻量：

- `apps/ai_models/services/`：`llm_services`（LLM 流式）、`realtime_asr` / `realtime_tts`（实时语音）、`tts` / `tts_adapters`（TTS 适配器）、`third_party_chatbots`（第三方机器人）、`agent_knowledge`（RAG 检索）、`reply_blocks`（回复块）、`follow_up_suggested_questions`（追问）。
- `apps/devices/services/`：`runtime`（设备运行时校验）、`chat_logs`、`chat_sessions`、`wake_words`、`voice_pipeline_logging`。
- `apps/resources/services/`：`command_dispatch`（控制指令派发）、`feishu`（飞书通知）。
- `apps/knowledge_base/services.py`：文档向量化、检索。

### 2.2.4 实时层（`config/realtime.py`）

统一 WebSocket 应用，约 2800 行，是系统最核心的运行时组件。详见 [04-数据流程图](./04-数据流程图.md) 与 [05-API接口文档](./05-API接口文档.md) 的 WebSocket 协议章节。

## 2.3 前端架构

### 2.3.1 技术选型

- **React 18 + TypeScript strict**：`noUnusedLocals` / `noUnusedParameters` / `noFallthroughCasesInSwitch` 全开，禁用 `any`。
- **Vite 8**：开发服务器（5173）+ 构建（`tsc -b && vite build`）。
- **Ant Design 5 + Tailwind 3**：Antd 负责数据密集型组件（Form/Table/Tree），Tailwind 负责布局与排版；Radix UI Themes 3 用于精细交互（Dashboard 创意卡片）。
- **Zustand**：唯一全局 store 为 `store/auth.ts`，其余状态局部化。
- **react-router-dom 6**：声明式路由 + 守卫。

### 2.3.2 目录约定

```
web/src/
├── api/            # client.ts (axios) + modules/<domain>.ts
├── components/     # brand-mark / status-tag / chat-markdown / knowledge-references
├── layouts/        # dashboard-layout（认证后外壳 + 移动端 Drawer）
├── router/         # 路由 + AuthGuard / GuestGuard / PermissionGuard
├── store/          # auth.ts（Zustand）
├── styles/         # index.css（全局类 + Tailwind 入口）
├── views/          # 28 个 kebab-case 页面模块
└── main.tsx        # ConfigProvider theme + BrowserRouter
```

### 2.3.3 路径与导入

- 相对 import，**未配置** `@/*` 别名。
- JSX runtime：`react-jsx`，无需 `import React`。
- 请求统一走 `httpClient`（`api/client.ts`），自动注入 Bearer，401 自动清登录态跳 `/login`。

## 2.4 跨层契约

### 2.4.1 鉴权双轨制

| 客户端 | 鉴权方式 | 入口 |
|--------|----------|------|
| Web SPA | JWT Bearer（`Authorization: Bearer <token>`） | `/api/v1/auth/login/` → access (30min) + refresh (7d) |
| Android 设备 | `X-Device-Code: <deviceCode>` 请求头 | `/api/v1/device-runtime/config/` 等设备接口 + `/ws/realtime/` |
| WebSocket | payload 内 `token` 或 query param（设备/租户维度） | `/ws/realtime/` 各 command 的 payload |

JWT 由自定义 `apps.accounts.authentication.TenantAwareJWTAuthentication` 解析，注入租户上下文。

### 2.4.2 统一响应包络

成功：DRF view 直接返回业务数据（由 renderer 序列化）。
失败：`config/exceptions.py` 统一转为：

```json
{
  "status": "error",
  "message": "错误信息",
  "code": 400,
  "data": null
}
```

字段验证错误：`message` 为分号拼接的字段错误；`data` 可选携带 `response_data`。

### 2.4.3 字段命名约定

- **前端 API 契约**：`camelCase`（如 `deviceCode`、`agentApplicationId`）。
- **后端模型字段**：`snake_case`（如 `device_code`、`agent_application_id`）。
- **映射层**：DRF Serializer 负责 snake_case ↔ camelCase 转换。

### 2.4.4 请求追踪

- `RequestIdMiddleware` 为每个请求生成 `X-Request-Id`，并透传上游 `X-Trace-Id`。
- WebSocket 命令通过 payload 内 `requestId` / `traceId` 字段追踪。
- 语音管线日志（`log_voice_pipeline`）按 stage 记录：`asr.request` / `asr.final` / `llm.request` / `llm.response` / `tts.request` / `tts.response`。

## 2.5 异步与并发模型

### 2.5.1 ASGI + uvicorn

后端必须以 ASGI 模式运行（`uvicorn config.asgi:application`）。原因：

- 聊天流式（SSE）依赖 `httpx.AsyncClient` + `async def` 生成器 + `StreamingHttpResponse`。
- WebSocket `/ws/realtime/` 需要 async 协程处理。
- 切换 WSGI 会导致流式输出被整段消费、WebSocket 失效。

### 2.5.2 Celery 双进程

| 进程 | 职责 | 启动命令 |
|------|------|----------|
| `celery_worker` | 执行异步任务（知识库向量化、媒体处理、飞书通知等） | `celery -A config worker -l info` |
| `celery_beat` | 定时调度（清理任务结果等） | `celery -A config beat -l info --scheduler django_celery_beat.schedulers:DatabaseScheduler` |

- Broker：Redis（`CELERY_BROKER_URL`，默认 db 1）。
- Result backend：`django-db`（`django_celery_results`）。
- 调度器：`config.celery_scheduler:ResilientDatabaseScheduler`，在 PostgreSQL 重启后自愈。
- 周期任务通过 `seed_operations_periodic_tasks` 命令注册到 `django_celery_beat` 表，由 Django Admin「周期任务」页面管理。

### 2.5.3 WebSocket 并发

`realtime_websocket_application` 为每个连接维护一个 `RealtimeConnection` 状态机，通过 `asyncio` 协程并发处理：

- 接收客户端消息（`receive_task`）。
- 订阅设备事件队列（`device_events_subscriber`）。
- ASR 上游流（`asr_upstream_task`）。
- LLM 流式（`llm_task`）。
- TTS 流式（`tts_task` / `agent_tts_worker`）。
- Agent 综合管线（`agent_task`）。

发送侧通过 `_RealtimeSendMonitor` + `asyncio.Lock` 串行化，避免并发写帧。

## 2.6 多租户隔离机制

### 2.6.1 数据层隔离

- 所有业务模型含 `tenant` 外键（`ForeignKey('tenants.Tenant')`）。
- `apps/tenants/managers.py` 的 `TenantManager` 在 queryset 默认按当前请求租户过滤。
- `apps/tenants/mixins.py` 提供视图级 mixin，自动注入 `tenant` 到 create/update。

### 2.6.2 权限层隔离

- 公司管理员与员工业务功能一致，仅员工无"员工管理"入口。
- 平台管理员通过 tenant scope 机制浏览各公司数据，不直接跨租户写。
- 普通公司账号不得通过 query 参数访问其他公司数据（queryset 强制过滤）。

### 2.6.3 设备层隔离

- 设备通过 `X-Device-Code` 认证，后端解析出 `device.tenant`，后续所有数据访问绑定该租户。
- WebSocket 命令通过 payload 内 `deviceCode` / `tenantId` 解析订阅范围。

## 2.7 缓存策略

- **默认缓存**：Redis（`django.core.cache.backends.redis.RedisCache`），与 Celery worker 共享。
- **业务缓存**：`config/business_cache.py` 提供命名空间化键管理，view 继承 `CachedBusinessResponseMixin` 复用。
- **开关**：`BUSINESS_CACHE_ENABLED`（默认开）、`BUSINESS_CACHE_TIMEOUT_SECONDS`（默认 300s）。
- **纪律**：禁止直接 `cache.set()` 业务键，必须走命名空间，否则跨进程清理失效。

## 2.8 可观测性

- **Sentry**：`sentry_sdk.init` 在 `settings/base.py` 顶部，`before_send` 过滤敏感数据；`send_default_pii=True`。
- **Request ID**：`X-Request-Id` / `X-Trace-Id` 贯穿 HTTP 与 WebSocket，便于日志关联。
- **语音管线日志**：`apps/devices/services/voice_pipeline_logging.py` 按 stage 结构化记录。
- **Celery 任务结果**：Django Admin「任务执行结果」页面查看。
- **SimpleUI Admin**：后台操作审计通过 `apps/audit/middleware.py` 的 `OperationLogMiddleware` 记录。

## 2.9 架构决策要点

1. **为何不用 WSGI**：流式聊天与 WebSocket 必需 ASGI。
2. **为何用 pgvector 而非独立向量库**：减少服务数量，PostgreSQL 内置向量检索满足知识库规模。
3. **为何单一 WebSocket**：避免业务 WS URL 爆炸，通过 `type` 命令路由，客户端订阅更简单。
4. **为何 settings 三层**：base 共享，dev/prod 差异化 DEBUG 与安全策略，避免环境耦合。
5. **为何 Celery 用 DatabaseScheduler**：定时任务可经 Admin 动态调整，无需重启；`ResilientDatabaseScheduler` 解决 PG 重启问题。
6. **为何前端不配 `@/*` 别名**：保持相对 import 简单，避免构建工具链额外配置。
